## October 1, 2026 Update

### Number Parsing

This week I implemented number parsing for the lexer. This was tricky to do with the existing implementation of the lexer, which lent itself to parsing greedily but not backtracking. I tried a different strategy this time, where I temporarily saved the position of the lexer, tried to parse part of a number, and then on success continued, but on failure backtracked to the stored state.

**SML Number Literal Rules:**
- There are two types of number literals in SML: integers and real numbers.
- An integer literal (of the `int` type) is written as: `[~]?(0|[1-9][0-9]*)`
    - In plain English, they are written as either '0' or a sequence of digits that don't start with '0', optionally preceeded by a '~' character, and NOT followed by an alphanumeric character.
- A real literal (of the `real` type) is written as an integer followed by, in order, one or both of:
    - A character '.' followed by one or more digits, i.e. `.[0-9]+`
    - A character 'E' followed by an integer, i.e. `E[~]?(0|[1-9][0-9]*)`

**How the number parsing algorithm works:**

- **`process_num`** tries to process a number literal...
    1. it tries `process_decimal` to get a decimal
        - if it gets a decimal, it then tries to get an 'E' character followed by an integer
            - if it can, it returns a real value with decimal and exponential form
            - otherwise, it returns a real value with only decimal form
    2. it tries `process_int` to get an integer
        - if it gets an integer, it then tries to get an 'E' character followed by an integer
            - if it can, it returns a real value with only exponential form
            - otherwise, it returns an integer value
    3. if `process_int` and `process_decimal` both fail, then `process_num` fails

- **`process_decimal`** tries to process a decimal number...
    - it tries `process_int` to get an integer, then tries to get a '.' character, then a non-empty string of digits
        - on success, it combines the integer before the point with the digits after the point, returning a real number
        - on failure, the previous lexer state is loaded and `process_decimal` fails

- **`process_integer`** tries to process an integer...
    - it gets a negative sign '~' if it can, and then succeeds iff the `process_unsigned_integer` procedure succeeds

- **`process_unsigned_integer`** tries to process an integer without the sign...
    - if the only character is a '0', it returns 0
    - otherwise it tries to return the integer built from getting a non-zero digit followed by any number of digits

### Lexer Rewrite

I rewrote the rest of the lexer code (excluding the process_string procedure) 
to use the same strategy of trying a case and then backtracking if it doesn't work. 
For the most part, I feel happy with the results, especially because it allowed me to write the lexer in a way where it only needed one pass. 
This technique is more flexible than using a 1-2 character lookahead to determine what type of token is being parsed, even if it is a bit more verbose in Odin.
I plan to use the same strategy to build the abstract syntax tree.

### Sample Cases

**Case 1:**
```sml
val (m, n): int * int = (123, ~25);
```

```
KEYWORD  val
KEYWORD  (
ALPHA_ID m
KEYWORD  ,
ALPHA_ID n
KEYWORD  )
KEYWORD  :
ALPHA_ID int
SYMBOLIC *
ALPHA_ID int
KEYWORD  =
KEYWORD  (
INT LIT  123 --> 123
KEYWORD  ,
INT LIT  ~25 --> -25
KEYWORD  )
KEYWORD  ;
```
